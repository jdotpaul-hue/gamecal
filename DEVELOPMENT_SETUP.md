## Getting started on a new machine

Use this when cloning, copying, or unzipping the repository onto a laptop that has never run Gamecal before. Git is optional; the same steps apply if you only have a folder tree.

### Prerequisites

| Tool | Version / note |
| --- | --- |
| Node.js | `24.22.0` (see `webapp/.nvmrc`; install via [nvm](https://github.com/nvm-sh/nvm) or the official installer) |
| pnpm | `11.25.0` (`corepack prepare pnpm@11.25.0 --activate` after `corepack enable`) |
| Container runtime | Docker Desktop, Colima, or OrbStack with the `docker` CLI on your PATH |
| Playwright Chromium | Only for `pnpm test:e2e`: `pnpm exec playwright install chromium` once per machine |

No global Supabase CLI is required; use `pnpm exec supabase` from `webapp` (pinned in devDependencies).

### First-time bootstrap

From the repository root:

```sh
cd webapp
corepack enable
corepack prepare pnpm@11.25.0 --activate
nvm use          # when using nvm
pnpm install --frozen-lockfile
```

Start the disposable local database (Docker must be running):

```sh
pnpm db:start
```

Create **`webapp/.env.local`** (ignored by git; not created automatically). Copy from `.env.example`, then set values from the local stack:

```sh
pnpm exec supabase status -o env
```

Use at minimum:

- `NEXT_PUBLIC_SUPABASE_URL` (local default `http://127.0.0.1:54321`)
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_...` from status output)

Never put secret/service-role keys in `NEXT_PUBLIC_*` variables.

Prove the tree:

```sh
pnpm verify       # lint, typecheck, format, unit tests, production build
pnpm test:db      # SQL/RLS/command pgTAP tests against the local stack
pnpm db:types     # regenerate src/types/database.generated.ts
pnpm dev          # http://localhost:3000
```

More Supabase detail: [webapp/supabase/README.md](webapp/supabase/README.md). App command reference: [webapp/README.md](webapp/README.md).

### Copying or zipping the repo to another laptop

**Bring the source tree** (Markdown plans, `webapp/` including `package.json`, `pnpm-lock.yaml`, `supabase/migrations/`, and `supabase/config.toml`).

**Do not rely on copying these**—reinstall or recreate on the destination:

| Path / artifact | Why |
| --- | --- |
| `webapp/node_modules/` | Run `pnpm install --frozen-lockfile` on the new machine |
| `webapp/.next/` | Regenerated by `pnpm build` or `pnpm dev` |
| `webapp/test-results/` | Playwright output; safe to omit |
| Docker volumes for `gamecal-webapp` | Local Postgres/Auth state; run `pnpm db:start` (or `pnpm exec supabase db reset`) on the new machine |
| `webapp/.env.local` | Machine-specific; recreate from `supabase status` after `db:start` |

You may include `webapp/src/types/database.generated.ts` in a zip for convenience, but after `supabase db reset` on the new machine run `pnpm db:types` so types match the applied migrations.

**Do not commit or share** `.env.local`, Supabase secret keys, or Docker-exported database dumps unless you intend to handle them as secrets.

### Everyday commands

| Goal | Command (from `webapp/`) |

## 5. Shared occurrence identity

Fix this protocol constant before creating any occurrence records:

```text
namespace = bf67d23d-270f-5606-bdb9-a90a143ad12d
name = <canonical lowercase definition UUID>:<original_scheduled_date YYYY-MM-DD>
occurrence_id = UUIDv5(namespace, UTF-8(name))
```

The namespace was derived once as UUIDv5 of the standard URL namespace and the opaque name `urn:gamecal:occurrence:v1`. It is a permanent literal protocol identifier: a later product rename does not change it. Reject invalid UUIDs/dates, normalize the UUID representation, and use no spaces, alternate date formats, effective reschedule dates or timezone suffixes in the name.

| Definition UUID | Original date | Expected occurrence UUID |
| --- | --- | --- |
| `fda923dc-3ebd-489e-a655-37e04fef3163` | `2026-10-14` | `55a014c9-4d95-5e15-9d2b-aac1953f81b8` |
| `fda923dc-3ebd-489e-a655-37e04fef3163` | `2026-10-15` | `5c75f0b0-ae34-5364-8804-247171556ce0` |
| `84915f93-ef45-4617-a753-0b072ab89ccd` | `2026-11-01` | `0a8f3101-1700-521b-bffe-423311e7b732` |

These vectors were independently computed with Python's standard UUID implementation and now pass in the scaffold's TypeScript `uuid` tests. PostgreSQL parity still requires the later local schema/extension implementation. Rescheduling retains the original ID/date anchor and the database uniqueness constraint. A namespace/encoding change after data exists would require an explicit compatibility migration.

## 6. Deterministic fixtures and script contracts

Keep fixtures at the boundary where they prove behavior, with fixed clocks and explicit zones. Shared expected values should cover:

- The UUID vectors above, original-versus-rescheduled date, duplicate creation and receipt payload normalization/hash behavior from the API contract.
- `America/New_York`, `2026-11-01 01:30`: earlier is `2026-11-01T05:30:00Z`, later is `2026-11-01T06:30:00Z`. A booked appointment must choose explicitly.
- `America/New_York`, `2026-03-08 02:30`: invalid booked wall time; the defined routine gap policy resolves to `03:30`. Do not let a library default silently choose product policy.
- All-day New York quests on `2026-03-08` and `2026-11-01`: due at `2026-03-09T04:00:00Z` and `2026-11-02T05:00:00Z` respectively; these dates span 23 and 25 hours. Add Singapore/UTC day-boundary and later itinerary endpoint cases as those features arrive.
- A revision such as `"9007199254740993"` remains an exact decimal string through SQL JSON, validation, IndexedDB and reconciliation.
- Zero initial XP, one accepted quest = 20 XP, undo = 0 XP, appointments = 0 XP; only a separate disposable milestone fixture starts at 80 XP.

The UUID and explicit DST fold/all-day values above were checked using Python standard libraries and the scaffold's TypeScript tests. SQL parity, recurrence generation and the integrated calendar journey remain unproven. Cover broader recurrence/timezone parity when recurrence is introduced.

## 8. Type-safety bootstrap gate

These options are configured in the scaffold's framework-compatible TypeScript project; this fragment is not a replacement for its complete Next.js configuration:

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "useUnknownInCatchVariables": true,
    "noEmit": true
  }
}
```

The [TypeScript option reference](https://www.typescriptlang.org/tsconfig/) documents these checks. Include maintained app, server, adapter and test code in an appropriate compiler project; do not hide code through broad exclusions or reduce these checks to accommodate a dependency. Keep framework-required generated types/configuration and isolate actual third-party declaration issues without weakening maintained-code checks.

Configure [type-aware typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/) alongside the installed Next.js ESLint configuration, verifying compatible versions. Enforce `no-explicit-any`, the `no-unsafe-*` rules for assignments/arguments/calls/member access/returns, `no-non-null-assertion`, `no-floating-promises`, `no-misused-promises` and `switch-exhaustiveness-check`. Do not assume the framework's lint defaults enable these rules. A lint run must actually load type information; syntax-only linting does not satisfy the gate.

Bootstrap/integrated-slice acceptance requires:

- `pnpm typecheck`, typed `pnpm lint` and `pnpm build` fail on real type violations; production builds cannot ignore type errors. During configuration, demonstrate representative invalid code is rejected, then remove temporary probes.
- Generate types from freshly applied local migrations and fail CI if the tracked result differs. All Supabase clients use that generated `Database` type, including privileged fixture clients.
- Define the first RPC request/response schemas and infer their DTOs. Runtime fixtures cover malformed success envelopes, wrong versions/entity tags, nullable/omitted fields and exact bigint strings; failed decoding preserves the pending command and confirmed cache.
- Verify persisted/outbox version decoding and unsupported-record recovery without resetting the queue. Include schema/command type checks that reject an invalid payload for a command and a meaningful mixed-up domain ID; use narrowly documented `@ts-expect-error` only in dedicated compile-time negative test cases, never as a production fix.
- Keep compilation, schema validation, SQL/RLS integration and browser journey results distinct. Type safety supports predictable changes; it is not a claim that a compiler proves security or business correctness.

Compiler/typed-lint checks and negative domain type cases are now executable. Temporary probes confirmed that unchecked indexed access, imprecise optional properties, explicit/propagated `any` and unhandled promises are rejected; the probes were removed afterward. The built placeholder passed its Chromium smoke test. Real generated database types, domain RPC schemas and SQL/RLS/queue checks remain later implementation gates. The CI workflow exists locally but has not run on GitHub.
